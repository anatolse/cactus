## Context

The `extern func` declaration already exists: a function with no body, whose implementation is provided in C++ by the backend or the user. `extern system` is the exact analogue for systems: a system declaration with no event handlers, whose implementation is provided by the backend or by the user in C++.

The existing `SystemNode` in the AST already has all the structural clauses needed (`filter`, `exclude`, `after_systems`, `order_by` from the dsl-system-order-by change). An `extern system` is simply a system declaration where the `handlers` list is absent by design.

The key question is: how does the backend know what to generate?

**Two cases:**

### Case 1: Stdlib-known patterns

The backend recognizes combinations of filter traits by their module path and field types:

| Filter includes | Backend generates |
|---|---|
| `std.render.sprites.Renderer` | Batched 2D sprite rendering (layer sorted) |
| `std.render.sprites.AnimatedSprite` | Sprite sheet animation frame advancement |
| `std.render.meshes.Renderer` | 3D mesh render submission |
| `std.render.meshes.PointLight` | Point light registration |
| `std.render.meshes.DirectionalLight` | Directional light registration |
| `std.physics.flat.*` body traits | Physics integration step |
| `std.audio.*` audio traits | Audio source playback management |

The stdlib declares these `extern system` declarations. Authors just apply the traits; the systems run automatically.

### Case 2: User-defined extern systems

For user-defined `extern system` with non-stdlib traits, the backend generates:
1. A typed C++ header with the system callback
2. The iteration infrastructure (view, sort if `order by:` present)
3. Calls the user callback for each matched entity (or batch — backend decides)

The generated signature follows a convention: `void <SystemName>_update(entt::registry& registry, <TraitA>& a, <TraitB>& b)` for per-entity, or `void <SystemName>_update(entt::registry& registry)` for batch (backend decides based on traits). The user implements this function in their C++ game code — same experience as `extern func`.

## Goals / Non-Goals

**Goals:**
- `extern system` syntax: filter, exclude, order by, after — same as regular system, no handlers
- Stdlib extern systems run automatically when their traits are applied to entities
- User-defined extern systems generate a typed C++ scaffold for user implementation
- Backend decides the optimal callback form (per-entity vs. batch) — not exposed in the DSL
- The stdlib `std.render.*` modules declare their passive systems as `extern system`

**Non-Goals:**
- Authors specifying the callback form (per-entity vs. batch) — this is a backend optimization
- `extern system` with handlers (contradiction — if you have handlers, use regular `system`)
- Cross-module extern system implementation resolution (user provides C++ in their game project)
- Runtime plugin system for custom rendering backends

## Decisions

### Decision 1: Syntax mirrors `extern func` — keyword prefix, no body

Just as `extern func` has no `:` and no body:
```cactus
extern func lerp(a: float, b: float, t: float) float
```

`extern system` has filter/ordering clauses but no handlers:
```cactus
extern system SpriteRenderer:
    filter:
        std.transform.flat.Position as pos
        std.render.sprites.Renderer as r
    order by:
        r.layer asc
        pos.pos.y asc
```

### Decision 2: Backend decides implementation form

The author never specifies per-entity vs. batch. This is a performance decision made by the backend based on the filter traits. For rendering, the backend batches; for custom user systems the backend generates per-entity; for complex cases the backend can generate whatever is most efficient. The DSL author is shielded from this choice.

### Decision 3: Stdlib passive traits connect to stdlib extern systems

The stdlib modules declare both the traits AND the extern systems. The author applies a `Renderer` trait; the `SpriteRenderer` extern system is pulled in automatically (it's in the same module as the trait). This mirrors how `std.core.Persistent` brings in the `SceneCleanup` system.

### Decision 4: User-defined extern systems generate typed C++ scaffold

For non-stdlib `extern system`, the backend generates a C++ header with a clearly-named function signature that the user implements. This is the same model as `extern func` — the compiler generates the header/stub, the user provides the implementation.

```cpp
// Generated by backend for:
// extern system MyParticleSystem:
//     filter: Position as pos, ParticleEmitter as pe

// In generated header:
void MyParticleSystem_update(entt::registry& registry,
                              entt::entity entity,
                              Position& pos,
                              ParticleEmitter& pe);
```

The user provides this function in their C++ game source.

## Risks / Trade-offs

- **Stdlib pattern recognition is a fixed list**: adding a new backend service (e.g., custom physics) requires updating the backend's known-pattern table. This is acceptable — the list is stable and changes rarely.

- **User-defined extern systems require C++ knowledge**: this is intentional. Users who need custom low-level behavior (particles, custom culling, etc.) are expected to be C++ developers. The DSL takes care of the ECS plumbing; they provide the domain logic.

- **Ordering between extern systems and regular systems**: an `extern system` participates in the same `after:` constraint graph as regular systems. This allows authors to sequence rendering after transform updates, etc.
